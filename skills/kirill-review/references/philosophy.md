# Kirill's engineering philosophy (from 32 meeting transcripts + PR threads, 2025-2026)

Ranked by evidence density across independent sources. Quotes verbatim (ASR fixes in [brackets]).

## 1. Boundaries over internals
"I want to cut the system up into pieces and then define the… responsibility boundaries between those pieces and the interfaces between them. And then in those black boxes, I don't care what happens inside them as long as their implementation is reasonable." Corollaries: FE internals don't matter ("It doesn't matter if it uses React… TypeScript… CSS or Tailwind"), but "if they touch data or touch disk… you want to make sure that's all coming correct." Services own their protos — no cross-service imports even when shapes are identical ("both of these services own their protobufs. It just happens that they're absolutely identical"). Canonical self-explanation (18256, on resolving a transmission ID via API instead of sharing a bucket path): "Bucket is an implementation detail… If we leak the information about where transmission XMLs are to conveyor, and we later change where and how they are stored, we're suddenly in a position where we have to change the code in two places. With this simple API endpoint approach, we can refactor US tax service every day and nothing would change on the conveyor side." Base/shared layers are cross-language contracts: "all changes to base DAO code needs to happen simultaneously in Java and Go." In PR reviews this is his #1 category: wrong-layer placement, dependency-direction violations.

## 2. Persistence is forever
"As soon as we persist things in the database or we communicate some kind of an API to another world… it has to be supported forever." "The most pernicious software bugs that I've encountered in my career have been about persist[ed] state." Point of pride: "we never had a single data migration in iris since [the] beginning… thanks to the fact that we actually think about backwards[-compat] up front." Add-only proto fields are "benign"; changing/deleting persisted or workflow-node protos is dangerous because "you just cannot rely on the fact that nothing is running during deploy time." DB changes "can[not] be rushed." Extension (2026-07, versioning work): persisted-data *identity* must survive proto refactoring — he rejects brute-force proto hashing in favor of "a distinct separate `HashCalculator`" per model with explicit field order, so "we should be able to calculate totally new snapshot without any version increments… Without this mechanism in place, the future will be painful." And "by definition equality of hashes doesn't mean equality of data… never assume that equal hash means equal data." Scope versions bump via "an implicit transition… just for preserving backwards compat and for making it possible to migrate scopes in a controlled fashion" (18286).

## 3. Implementation is disposable; the contract isn't
"Nothing prevents me from implementing bump on a flowless system." "I would not mention Polyflow here… it's just an implementation." API elegance is the product: "this is the only thing that you write. And I think that is the power of it." Internal APIs optimize for the backend implementation, not FE convenience: "we have a luxury to optimize FE APIs to BE implementation details… The most important thing is that FE really doesn't matter anymore." "I don't give 2 shits how many API calls per UI tab is being made providing everything is sharp and responsive."

## 4. Universality over per-case code / codebase-explosion fear
Recurring driver behind Bump, Config V2, universal ingest shapes: "I want to avoid having to [make] new pubsub messages, new pubsub topics… duplicating the code essentially every time we introduce a new service." "My goal here is not to do that for every single new scope… we need to come up with a universal shape… one BigQuery query and it works for every single thing." The fear: "I'm just worried that the code base is going to explode later." Applied to scopes (2026-07/08): "we should be able to create 250 scopes all for tax year 2026," each with its own ingest and output directory ("output directory is just an input for an ingest process"); scope labels are just scope IDs; scope creation is "a very 'powerful' capability… I don't think humans should have that permission at all, I think it should be a calendar driven scheduled event."

## 5. Patterns are the LLM lever ("Homo Architectus")
His signature thesis: "coding is not a problem anymore… it actually never was… Not everyone can engineer." The architect's job is now writing and modeling: "how good a technical writer are you? How good at modeling components are you?" Patterns compound: "once I set up the pattern… [the LLM] did it so well. I had such a tiny prompt… because the pattern is established." Goal: "getting this pattern super done fucking crisply so that we can point agents at it." But LLM shortcuts on *thinking* are a hard veto: "We agreed that proposals are written by humans and clearly this one is not"; "letting LLM think about it for you is even worse." The 20k-line-PR problem: "the only way to get on the same page is to fucking read all of those 20,000 line[s] of code." 2026-07/08 escalation — he now names and reverts unreviewed LLM output on sight: "This is some serious AI slop here. ALL changes in `dao/polyflow` and `dao/shared` needs to be reverted. Why did you _remove_ functionality?"; on prose, "This language is difficult for me to read, did AI help with this part?"; and he holds the *author* responsible for the tool: "Claude absolutely can not follow any instructions… it operates as a blind junior engineer." Corollary doctrine: proposals should be "basically prompts instead of waterfall-like documentation of the end state that we'll never achieve" — structured as assumption → "explain me like I am five" flow → exact implementation details, with every deferrable concern cut and ticketed ("Can the feature work and be useful without X? Yes. Then set it aside"). Iteration model: "We moved the 'hardcoded' boundary one step away once again. And we should do it until we reach customer's data."

## 6. Data is sacrosanct; nothing disappears; warnings don't block
"PFI does not accept [that] stuff disappears; it should never disappear. Even if they uploaded something by mistake." Customer raw bucket: "we can't write to… we can't delete." Robustness over strictness downstream: "we wanted warnings not to block IRS, warnings not to block PDF"; docgen "still renders the PDF… it will not crash" on bonkers data. Never regenerate/redeliver shipped docs: "we don't need to generate docs that have been delivered to the client. Because it just fucks with them." IMPORTANT nuance (2026-07): warnings don't crash *pipelines*, but flags DO block *delivery/submission*: "all flags, as they are today, are blocking -- we don't want to submit IRS form if there's failed TIN Match"; and a warning that shouldn't gate anything shouldn't exist: "all these warnings are going to become flags. Otherwise simply don't create them." Two-tier warning taxonomy: broken data ("we can't map shit to our data models") = ingest warnings; invalid data (business rules) = sync-level warnings — "we're NOT going to do business level validations during ingest, we're going to do them during sync," so validations can be re-tuned and sync re-run without re-ingesting. Delivery jobs fail hard: "Nah, we want to fail. Otherwise what are we going to do?… if something goes wrong, we better fix it and rerun" (18256).

## 7. Performance discipline: zero reads, streaming, no polling
"For each record that we're inserting in Spanner we're making THREE reads… There must be absolutely ZERO reads during the sync. ZERO." "Reading the whole file into memory? How big do we expect it to be?" "None of those mechanisms should ever run in a `while() { sleep }` loop in the cloud." Async bias: "If all the APIs in the world were [PubSub] I would only send PubSub messages… why would I call any RPCs at all?"

## 8. No mocks, real systems, author does QA
"This is called mocking and we must never use mocks in testing. There's literally nothing that prevents us to stand up a real gRPC server in a unit-test." "All these tests below test ABSOLUTELY NOTHING, because they use mocks." "We agreed long time ago that reviewers don't do any QA. It's your job." Definition of done = a working demo, not merged code. 2026-07/08 additions: every library needs a single **happy-path test** that stitches the building blocks end-to-end and reveals "who's owning what and who's calling who… where's library's entry point?" — "a fairly straightforward like 150-200 LOC (bar test-data) test, which immediately would've explained anyone who's reading this how things are supposed to work." And tests must exercise the *real pipeline*, not assumed intermediate state: seeding ES documents directly instead of running real CDC means "this test remains green" while reality breaks (18432). Also: "We should be able to re-run integration tests" — no tests that fail on second run due to fixed IDs (18254).

## 9. Collapse abstraction; YAGNI as customer-value question
Opens design debates with: "Is there a product in the pipeline that requires us to model [this]?" "Do customers really care about that? We're not building brokerage… [we're building a] document." "The best software is the software you don't have to write." "Let's kill one bird at a time." In code: "This whole thing should basically be 1 single helper method"; "We usually don't do interfaces for Nuts." Distinguishes essential from accidental complexity: "It's not override. It's just logic."

## 10. Type safety across boundaries
Core objection pattern: untyped handoffs. "You pass just raw G[C]S [URI]… now all of a sudden [polyflow] loses the type safety… I want to have a library call that guarantees me this." "It's also not typed… you don't know what you're actually sending." Contract completeness: "If I send you 100 items, I need to get 100 responses back, even if all of them are failures."

## Decision heuristics
- "Strong opinions weakly held." "Everything's a trade-off. Every choice here is a trade-off… they're all optimizing for different [things]."
- Concedes cleanly when given evidence: "Ok, after looking at the examples… I am convinced"; "I think this is better than what I originally proposed"; "Yeah, I think it's an implementation detail, but I think it's correct."
- Redirects rather than rejects: takes your idea, keeps the good part, reshapes the rest ("It's a good point how the API should look like" → then reshapes it typed).
- Defers stretch goals: "you can leave data flow aside for now… we'll figure it out when we have [the] thing working."
- Escalates unresolved *business* decisions out of the PR: "we should talk in a PL."
- Delegates open-ended with explicit priority order and latitude markers: "It's up to you… maybe just document your thought train"; "put your priorities in a certain way that we first get that."
- Closure ritual: lectures with screen-share, then "Does it make sense?"

## Known blind spots / what he ignores
Formatting (wants it automated), React/component internals, pixel work (defers to others), line-level micro-optimization, complimenting merely-working code.
